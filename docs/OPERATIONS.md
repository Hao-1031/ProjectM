## 1. 核心决策摘要

| 决策维度 | 结论 |
|----------|------|
| 商业模式 | Web 端免费 + 外观内购（无氪金数值） |
| 增长策略 | 渐进式：先小规模验证留存（DAU 100-500），数据达标后扩量 |
| 核心留存驱动 | 战术深度（据点防守 + 英雄/武器组合策略），但需降低入门门槛 |
| 入门策略 | 前 3-5 局「引导模式」：自动推荐武器、简化 AI、逐步解锁复杂度 |
| 目标用户 | 策略/动作游戏爱好者，通过渐进难度曲线匹配 Web 轻度用户到硬核玩家 |
| 变现设计 | 赛季通行证 + 英雄皮肤 + 武器外观 + 表情/徽章，全外观无数值加成 |
| 内容更新 | 月度赛季制（初期），后续按数据调整节奏 |

## 2. 产品现状分析

### 2.1 核心优势

| 优势 | 说明 |
|------|------|
| 战术深度 | 7 英雄 × 24 武器 × 20 敌人 × 10 Boss × 4 地图，组合空间大 |
| 无氪金 | 核心差异化卖点，商店/通行证/皮肤仅售外观，不卖数值/英雄/抽卡 |
| 双算法驱动 | α 动态节律算法 + β 智能行为算法，AI 自适应难度与行为 |
| 9 种游戏模式 | 战役、生存、无尽、日常、防御、极限生存、旗舰、死亡竞赛、肉鸽 |
| Web 零门槛 | 浏览器即玩，无需下载安装，获客成本极低 |
| P2P 联机 | WebRTC 最多 4 人，无需中心服务器承载游戏流量 |
| 旗舰版内容 | 赛季系统、近战武器、英雄技能增强、官网史诗叙事、排行榜 |

### 2.2 当前短板

| 短板 | 影响 | 优先级 |
|------|------|--------|
| 新手引导缺失 | 新玩家前 5 分钟流失率可能极高 | 高 |
| 外观数量不足 | 变现能力弱，赛季通行证吸引力有限 | 中 |
| 社区功能缺失 | 无好友系统、无聊天、无分享，社交传播为零 | 中 |
| 无数据埋点 | 无法量化留存率、付费转化、关卡通过率 | 高 |
| 反外挂空白 | Web 端易被修改，无校验机制 | 中 |
| 移动端未适配 | 仅 PC 端，损失大量潜在用户 | 低 |

## 4. 玩家留存策略

### 4.1 核心留存循环

```
新手引导（3-5局）→ 战术探索（英雄/武器组合）→ 赛季目标（通行证进度）→ 社交分享（排行榜/回放）→ 回归
```

### 4.2 分层留存机制

**短期留存（Day 1-7）：**

| 机制 | 说明 |
|------|------|
| 引导模式 | 前 3 局自动推荐英雄/武器，简化 AI，保证通关体验 |
| 每日挑战 | 固定种子 + 排行榜，每天 1 次，制造"每日必玩"习惯 |
| 首周奖励 | 登录 7 天送基础皮肤，建立付费认知 |

**中期留存（Day 7-30）：**

| 机制 | 说明 |
|------|------|
| 赛季通行证 | 30 天一个赛季，免费 + 付费双轨，进度可视化 |
| 英雄解锁 | 通过游戏内货币解锁英雄（非付费），提供短期目标 |
| 武器大师 | 每把武器独立熟练度，满级解锁专属涂装 |

**长期留存（30 天+）：**

| 机制 | 说明 |
|------|------|
| 排名系统 | 赛季段位 + 全球排行榜，竞争驱动 |
| 内容更新 | 月度新英雄/武器/Boss，保持新鲜感 |
| 社区内容 | 战斗回放分享、战术讨论、玩家自制挑战 |

### 4.3 关键留存指标

| 指标 | 目标（初期） | 目标（规模化） |
|------|-------------|---------------|
| D1 留存 | > 40% | > 45% |
| D7 留存 | > 20% | > 25% |
| D30 留存 | > 10% | > 12% |
| 平均游戏时长 | > 15 分钟 | > 20 分钟 |
| 平均每日游戏次数 | > 1.5 | > 2.0 |

## 5. 技术运维策略

### 5.1 架构优势

- **WebRTC P2P**：游戏流量不经过中心服务器，服务器仅承载页面和 API
- **Next.js standalone**：单进程部署，运维简单
- **Supabase**：托管数据库，免运维

### 5.2 监控与告警

| 层面 | 工具 | 监控内容 |
|------|------|----------|
| 应用层 | PM2 + 自定义日志 | 进程状态、内存、CPU、重启次数 |
| 业务层 | 自建埋点（推荐） | DAU、留存、付费、关卡通过率、模式分布 |
| 错误层 | Sentry（可选） | 前端/后端异常堆栈 |
| 服务器层 | 阿里云监控 | CPU、内存、磁盘、网络 |

### 5.3 扩容路径

```
初期：单台 2C4G ECS → DAU 500+
中期：升级至 4C8G + CDN → DAU 2000+
后期：多实例 + 负载均衡 + 独立数据库 → DAU 5000+
```

> 由于 WebRTC P2P 架构，游戏流量不经过服务器，扩容压力远低于传统 C/S 架构游戏。

## 6. 风险管控

### 6.1 风险矩阵

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|----------|
| 玩家流失率高 | 高 | 高 | 引导模式 + 每日挑战 + 数据驱动迭代 |
| 外挂/作弊 | 中 | 高 | 客户端校验 + 服务器验证 + 举报系统 |
| 收入不达预期 | 中 | 中 | 控制成本（初期 ~110 元/月），外观设计提升吸引力 |
| Supabase 服务中断 | 低 | 中 | 本地存档兜底，核心玩法不依赖数据库 |
| 竞品冲击 | 低 | 低 | 战术深度 + 无氪金差异化，不易被复制 |
| 版权/合规 | 低 | 高 | 外观设计原创，避免侵权 |

### 6.2 反外挂策略

| 层级 | 措施 |
|------|------|
| 客户端 | 关键数值校验（伤害、金币、经验），异常检测上报 |
| 服务器 | 排行榜提交附带校验哈希，验证游戏时长与分数合理性 |
| 社区 | 举报系统 + 人工审核 + 封禁名单 |

## 10. 总结

Project-M L3V100 旗舰版具备成为精品 Web 游戏的潜力：

- **战术深度**是核心竞争力，但需要**引导模式**降低入门门槛
- **无氪金**是差异化卖点，在当下氪金泛滥的市场中稀缺
- **WebRTC P2P**架构使运维成本极低，初期 ~110 元/月即可运营
- **渐进式增长**策略务实，先验证留存再投入推广
- 最大风险是**玩家留存**——引导模式 + 每日挑战 + 赛季系统是核心应对策略

**一句话总结：** 用战术深度留住核心玩家，用引导模式降低入门门槛，用赛季通行证变现，用渐进式增长控制风险。
